# 실험 3 — MIDI. 슬룻이 옳았던 유일한 경우

**이 저장소의 중심 비유를 직접 쟀다.**

MIDI 는 "작은 키 + 거대한 디코더" 구조가 실제로 동작하는, 확립된 사례다.
슬룻이 주장한 것과 구조가 같다. 다른 점은 **아무도 그것을 압축이라고
부르지 않는다**는 것뿐이다.

## 읽는 법

**MIDI 는 1/89 크기로 mel 거리 0 을 낸다.** Opus 는 89배를 쓰고도 못 맞춘다.
EnCodec 은 20배를 쓰고 더 나쁘다.

이것만 보면 슬룻이 옳았던 것처럼 보인다. **회계를 마저 해야 한다:**

```
MIDI 파일         2,958 바이트
사운드폰트     5,969,788 바이트     ← MIDI 의 2,018배
```

**그리고 조건이 하나 더 있다.** MIDI 는 *그 사운드폰트로 렌더링한 바로 그
소리* 만 재현한다. 다른 사운드폰트를 쓰면 다른 곡이 된다. 우리가 원본으로
삼은 파형 자체가 사운드폰트가 만든 것이므로, **MIDI 는 자기가 만든 답을
맞힌 셈**이다. 시험 문제를 낸 사람이 시험을 본 것이다.

Opus 와 EnCodec 은 그 특혜가 없다. 임의의 파형을 받아서 맞춰야 한다.

## 그래서 무엇이 증명되는가

**"모델을 공유하면 전송량이 극단적으로 준다" 는 명제 자체는 참이다.**
MIDI 가 40년간 그렇게 해왔다. 1/89 는 과장이 아니라 실측이다.

**그리고 동시에, 그것이 왜 일반적인 압축이 될 수 없는지도 보여준다:**

| 조건 | MIDI | 임의의 오디오 |
|---|---|---|
| 내용이 모델의 표현 범위 안에 있나 | **그렇다** (그 소리를 만든 게 모델이니까) | 아니다 |
| 원본이 유일하게 정해지나 | 아니다 — 사운드폰트마다 다르다 | 그렇다 |
| 새 음색을 담을 수 있나 | 못 담는다. 사운드폰트에 먼저 넣어야 한다 | 담는다 |

**슬룻의 오류는 세 번째 칸을 첫 번째 칸처럼 팔았다는 데 있다.**
"어떤 영화든 8 KB" 라고 했지만, 실제로 가능한 것은 "내 370 MB 안에 이미
있는 16편 중 하나를 4 KB 로 고르기" 였다.

## 세 실험을 나란히 놓으면

| | 대상의 구조 | 결과 |
|---|---|---|
| [영상](results-01-vae-latent.md) | 약함 | **진다** — x264 에게도 |
| [오디오](results-02-audio.md) | 강함 | **이긴다** — Opus 대비 5~15배 |
| MIDI | **모델이 곧 대상을 정의** | **압도한다** — 89배, 오차 0 |

**축이 하나다: 내용이 모델의 표현 범위에 얼마나 들어와 있는가.**

MIDI 는 그 범위가 곧 내용의 정의다(100%). 음성과 음악은 물리적·문법적
제약 덕에 상당 부분 들어온다. 일반 영상은 거의 안 들어온다.

그리고 범위 밖의 것은 **비트를 더 준다고 돌아오지 않는다.** 세 실험 모두에서
천장이 관측됐다. 차이는 그 천장이 쓸모 있는 자리에 있느냐뿐이었다.
